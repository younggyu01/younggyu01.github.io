개인 노트북에 회사 자료를 옮겨도 되나요?

원칙적으로 안 됩니다. 회사 자료는 승인된 기기에만 끊김보관할 수 있습니다. 재택근무처럼 꼭 필요한 경우에는 보안 담당 부서의 승인을 먼저 받아야 합니다.

도중에 끊겼습니다. 여기까지만 도착했습니다.비정상 종료를 감지했습니다. 수신한 부분까지만 표시합니다.

동작을 직접 눌러 볼 수 있게 만든 예시입니다. 실제 제품 화면은 아니며 문답도 예시입니다.

  1. 직원마다 맡은 역할이 다르고, 역할에 따라 보여야 할 화면도 다릅니다. AI의 답변은 한 글자씩 도착하기 때문에, 도중에 끊겨도 겉으로는 끝난 것처럼 보일 수 있습니다.

    역할 기반 접근 제어와 SSE 스트리밍이 한 화면에 있으면, 권한이 잘못 적용되거나 스트림이 비정상 종료되어도 화면에서는 드러나지 않기 쉽습니다.

  2. 챗봇과 교육, 퀴즈 화면을 만들었습니다. 로그인한 사람의 역할에 따라 메뉴와 화면이 달라지게 했고, 답변이 끝까지 도착했는지 도중에 끊겼는지를 구분해 화면에 표시했습니다. 교육 자료를 올리면 대본 생성, 검토자 승인, 영상 생성, 게시까지 이어지는 제작 과정도 구현했습니다.

    React와 TypeScript로 챗봇, 교육, 퀴즈 UI를 구현했습니다. Keycloak과 JWT의 역할 정보로 화면 접근을 나누고, REST와 SSE 응답의 종료 상태를 구분해 처리했습니다. 교육 영상 제작은 자료 업로드(S3 presigned URL)부터 스크립트 생성, 검토 승인, 영상 생성, 게시까지를 단계별 상태로 구현했고, Spring, FastAPI 서버와 연동했습니다.

  3. 사용자는 지금 보는 답변이 온전한지 화면에서 바로 알 수 있고, 자기 역할에 맞는 화면만 보게 됩니다. 이 프로젝트는 SK쉴더스 루키즈 4기 최종 팀 프로젝트에서 대상을 받았습니다.

    스트림의 정상 종료와 비정상 종료가 UI 상태로 구분되고, 역할에 맞지 않는 화면은 열리지 않습니다. SK쉴더스 루키즈 4기 최종 팀 프로젝트에서 대상을 받았습니다.

동작을 직접 눌러 볼 수 있게 만든 예시입니다. 실제 제품 화면은 아니며 라인 이름과 기록은 임의로 만들었습니다. 기록 한 줄을 누르면 고치기 전의 원본이 보입니다.

  1. 리크 검사는 제품에 새는 곳이 없는지 확인하는 검사입니다. 보안 때문에 검사 장비와 직접 연결할 수 없어, 그동안 쌓인 엑셀 파일을 그대로 써야 했습니다. 그런데 같은 라인과 같은 날짜가 파일마다 다르게 적혀 있어, 그대로 합치면 한 라인의 기록이 여러 라인의 기록처럼 나뉘어 집계됩니다.

    보안상 장비 연동 대신 검사 결과 XLS가 입력이었습니다. 라인, 날짜 표기가 일정하지 않아 정규화 없이 적재하면 같은 라인의 데이터가 서로 다른 키로 갈라집니다.

  2. 엑셀 파일을 읽어 라인 이름과 날짜를 하나의 형식으로 맞춘 뒤 저장했습니다. 같은 이름의 파일이 다시 들어오면 유지, 건너뛰기, 교체 중에서 고르게 했고, 어느 라인인지 알 수 없는 파일은 짐작하지 않고 사용자에게 묻게 했습니다. 어떤 파일이 언제 들어왔는지 이력을 남기고, 잘못 들어간 기록을 지우거나 다른 라인으로 옮기면 그 변경도 기록되게 했습니다. 저장된 데이터는 백업 파일 하나로 내보내 다른 컴퓨터에서 그대로 복원할 수 있습니다.

    Python으로 XLS를 파싱해 라인과 날짜를 표준화하고 SQLite에 적재하는 저장 계층을 맡았습니다. 파일 불러오기(중복 파일의 유지, 건너뛰기, 교체), 적재 이력, 원본 조회(행 삭제, 라인 이동, 변경 이력), 데이터 이전(백업과 복원)을 구현했고 PySide6 화면 작업을 함께 했습니다.

  3. 화면에 보이는 숫자가 어느 파일에서 왔는지 원본까지 거슬러 확인할 수 있습니다. 최종 검증에서는 한 라인에 쌓여 있던 검사 파일 2,909개를 기존 방식과 새 방식으로 각각 읽어, 모든 파일에서 결과가 같은지 대조했습니다. 프로그램은 한일전기 세종공장에 배포됐습니다.

    표준화한 값과 원본 행을 함께 보존해 집계 결과를 원본까지 추적할 수 있습니다. 최종 검증에서 대상 라인의 일일보고서 XLS 2,909개를 기존·신규 파서로 각각 읽어 대조했고 불일치는 0건이었습니다. SQLite 저장은 실제 파일 100개로 세 번 반복해 매회 17,430행이 들어가는 것을 확인했습니다. 한일전기 세종공장에 배포됐습니다.

    Spring Boot, JWT, MariaDB로 caseId 기반 점검 오케스트레이션 API를 만들고 멱등성 키를 적용했습니다. LSTM 분석 서버(FastAPI), Simulation Adapter와 Worker, 웹, Isaac 시뮬레이터를 연결했고, 물리 버튼으로 요청을 보내는 RV101용 Android(Java) 앱을 개발해 실기기에서 검증했습니다.

  3. 응답이 끊긴 상황을 재현해, 다시 요청해도 점검 기록이 한 건으로 유지되는 것을 확인했습니다. 시뮬레이터가 멈춰 있으면 글래스가 그 사실을 알려 줍니다. 실제 글래스로 요청을 보내 이 안내가 뜨는 것을 확인했고, AI 분석과 시뮬레이터 연결도 구간별로 각각 확인했습니다.

    응답 유실을 재현해 같은 멱등성 키로 재요청하면 HTTP 200과 Idempotent-Replayed: true가 돌아오고 점검 건이 1건으로 유지되는 것을 확인했습니다. RV101 실기기 요청에서는 503 SIMULATION_UNAVAILABLE이 HUD에 표시됩니다. 합성 CNC 데이터의 LSTM 분석, 시험용 Worker 처리, 실제 Isaac Sim 단일 요청(HTTP 200, scene load, reset, readback)은 구간별로 따로 검증했습니다.

설계에서 지킨 것

  • 글래스는 창구, 중심은 서버

    글래스 앱과 웹 화면이 같은 서버 창구를 거칩니다. 더 좋은 기기가 나오면 기기만 바꾸면 되고, 글래스가 없는 곳에서는 웹으로 같은 일을 할 수 있습니다.

    RV101 앱과 웹이 AI Agent를 직접 부르지 않고 점검 오케스트레이션 API를 단일 진입점으로 씁니다. 특정 기기에 종속되지 않는 구조입니다.

  • 판단은 사람이 한다

    AI 분석 결과가 곧바로 다음 검증이나 장비 조작으로 이어지지 않습니다. 필요한 확인은 사람이 골라 요청하고, 마지막 판단도 사람이 합니다.

    LSTM 분석과 Isaac 검증을 자동으로 연쇄 실행하지 않고 독립 계약으로 따로 호출합니다. 검증 결과의 MATCHED는 장면 조건이 반영됐다는 뜻이며 안전 승인이 아닙니다.

  • 모르는 것은 모른다고 표시한다

    응답을 받지 못하면 성공이나 실패로 단정하지 않고 같은 요청으로 다시 확인합니다. 시험용 환경에서 나온 결과에는 시험 결과라고 표시합니다.

    응답 유실 시 동일 멱등성 키로 처리 결과를 재확인합니다. 시험용 Worker의 결과와 실제 Isaac Sim의 결과를 구분해 표시합니다.

  • 기존 설비는 그대로 둔다

    설비를 새로 바꾸지 않고 필요한 기능부터 하나씩 붙일 수 있는 구조입니다. 실제 공장에 적용해 효과를 재는 일은 다음 단계로 남아 있습니다.

    Port와 Adapter로 실행 환경을 계약 뒤에 두어 Agent와 Worker를 단계적으로 추가하고 교체할 수 있습니다. 현장 실증은 향후 과제입니다.
